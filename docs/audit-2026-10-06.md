## Summary

The core is in good shape: integer-cent money, server-authoritative bag pricing, hashed guest tokens, frozen order snapshots, a migrations-only gate and a create-only seed are all done well, and drafts do not leak over REST. There are **no critical findings**. There are **4 high findings**:

- **A01.** A crafted `startReservation` call lets a customer pay for fewer items than staff are told to pack. It bypasses the repeat, premium and stock limits.
- **A02.** Order and reservation numbers come from `count + 1`. Deleting any order, which the owner can do and which is the obvious pre-launch cleanup, makes every later checkout fail permanently.
- **A03.** The first account to open `/admin` on a fresh public deploy becomes the owner.
- **A04.** The public REST API exposes hidden products, staff-only assembly notes, exact stock and reserve counts, and unapproved prices.

**11 medium findings** follow. The main ones are:

- unapproved prices shown on the storefront
- no default closed dates (Dec 25, Jan 1 and Labor Day are offered as pickup days)
- no security headers, and a non-`Secure` Payload cookie
- `APP_ENV` fails open to the test payment provider
- latent milestone-6 payment defects in `service.ts`
- a form reset that wipes the contact fields after any server error (a WCAG 3.3.7 problem)

The 8 low findings cover error pages, the mobile menu, small accessibility items, seed side effects, audit gaps, dead code and docs, test and CI gaps, and admin hygiene.

Missing stock decrement, holds and sync (AC 04) are not ranked as findings: they are known and planned for the wave-2 inventory agent. They are recorded in the AC table.

## Details and traces

**A01.** `validateGift` merges by `productId` (`validate.ts:17-21`), so `[{P,3},{P,-2}]` becomes P x 1: `REPEAT_LIMIT` (`maxPerGift` 1), the premium cap and the stock check all pass. `priceBasket` then runs `draft.request.selections.filter(s => s.quantity > 0)` (`service.ts:290-292`), giving P x 3. The totals use the validation's `contentsCents` (P x 1). The tax uses the components (P x 3). `assemblyInstructions` prints "3 x P". The input reaches `priceBasket` through `startReservation` (`actions.ts:26-34`), which only validates with `validateGift`, and then through the signed `sp_basket` cookie. The signature proves the server saved it, not that it is clean. The builder UI cannot produce duplicates, so normalising in `parseCustomRequest` changes no honest flow. Payments are test-only today, so there is no live money loss yet, but staff would be packing the wrong basket.

**A02.** `nextNumber` = `totalDocs + 1` (`service.ts:163-166`). The loop in `createOnce` (`:177-188`) recomputes it unchanged each attempt, then rethrows at `attempt >= 4`. Order creation is `create: nobody`, so only code can create orders, and only code can fix this. Pre-launch tidy-up of test orders is exactly the trigger.

**A03.** Payload's `first-register` is open while the users table is empty, and `firstUserIsOwner` makes whoever uses it the owner. The README and `preview-and-sharing.md` already warn about this for the local tunnel, but there is no equivalent step for the cPanel deploy, and no deploy runbook exists in the repo.

**A04.** Draft safety is fine (see "Verified safe"). The leak is the `hidden` channel, the staff-only fields and the unapproved prices. Fields read by the storefront (`stockQuantity`, `stockState`, `onlineReserve`, `priceApproved`) are needed anonymously by `queries.ts`, so field-level `read` would break the shop. `BasketBuilder` is a client component and receives `products[].stock.quantity`; cap it to `maxPerGift` (semantics unchanged for any quantity the rules allow). No client code calls `/api/*`, so closing anonymous product REST reads breaks nothing on the storefront.

**A05.** `orderingState(provider, taxApproved)` is correct (`payments/index.ts:31-35`), but both services call it with a literal `false` before pricing. Pages call it correctly, so the form renders, then the action refuses. Tests only exercise "no provider" and "test provider".

**A06.** `sellableMax` and `availabilityOf` correctly refuse unapproved prices, so nothing can be bought. Only the display is wrong. The three ceramics have `priceApproved:false` in `catalog.json`.

**A08.** `extractJWT` accepts any Origin when `csrf` is empty. Server actions are covered by Next's own Origin-versus-Host check (see "Verified safe"). The gaps are the Payload API and cookies. Payload's `getFile` sets a CSP only on uploaded files, and nothing else sets frame or HSTS headers. HSTS and HTTPS redirects may also be set at the cPanel or LiteSpeed layer. That is outside the repo, so confirm it there.

**A09.** The tests pass `APP_ENV: "test"` (`tests/setup-env.ts`, `checkout.test.ts`), so the allowlist must include `test`.

**A13.** `startHostTransition` calls `requestFormReset` before running a function form action (`react-dom-client.development.js:8955`); the reset applies when the transition commits. The reset happens whether the action returns an error or succeeds.

**A15.** `ensureBagToken` accepts any 20-64 character `[\w-]` cookie value as a bag token, so the token need not be server-issued. That is harmless (the hash is the key) but means cart creation is fully client-driven.

## Verified safe (so nobody "fixes" these)

- **Drafts over REST.** `Products.read` returns `{_status: published}` for anonymous. With `draft=true` Payload rewrites it to `version._status` (`find.js:103-104`), and `readVersions` falls back to "must be logged in" (`executeAccess.js`).
- **GraphQL playground.** Served only when `NODE_ENV !== "production"`, and `disablePlaygroundInProduction` defaults to true, so it is a 404 in production. (A08 covers `POST /api/graphql`, which is enabled.)
- **Server-action CSRF.** Next compares Origin with Host or `x-forwarded-host` and allows only POST (`data-security.md`, `serverActions.md`). Confirm LiteSpeed forwards `x-forwarded-host`, or set `serverActions.allowedOrigins`.
- **Uploaded files** are served with a restrictive CSP (`payload/dist/uploads/endpoints/getFile.js:112`), and SVG is not an allowed MIME type.
- **Guest tokens.** URL tokens are HMAC-SHA-256 (256 bits), only the hash is stored, and `accessTokenHash` is unreadable (`read: () => false`). The lookup is DB equality on the hash, which is not practically timing-exploitable. The basket cookie uses `timingSafeEqual`.
- **Secrets.** None in the repo or git history (`.env*` ignored, `.data` ignored, `.env.example` empty). Logs print only order numbers, with no PII.
- **overrideAccess.** Every `overrideAccess: true` is server-internal. Storefront catalog reads use `overrideAccess: false`.
- **Bag cookie.** httpOnly, SameSite=Lax, Secure in production; it holds no prices.
- **Tax and money.** Half-up per line (`tax.ts:21`), deposit half-up and capped (`deposit.ts:12-13`), integer assertions everywhere. Pickup timezone and DST logic is correct (`pickup.ts:25-46`).

## Pre-merge checklist for the wave-1 branches (derived from this audit)

- **`inquiries`:** the new collection must have `create: nobody` (the form posts through a server action using the Local API), `read` staff-only, and no anonymous REST create. Add input limits and a honeypot, and plug it into the A15 limiter.
